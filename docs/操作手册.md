## 0. 环境准备

```powershell
# 1) Python ≥ 3.12
python --version

# 2) 安装依赖（在仓库根 d:\biancheng\otherProject\my_buddy 下执行）
#    注意用 `python -m pip` 而不是裸 `pip`：后者可能被 PATH 上其他 Python 抢走，
#    把依赖装错到全局 site-packages（详见 §4 常见问题）
python -m pip install -r requirements.txt

# 3) Playwright 浏览器内核（动态页兜底用；只装一次）
python -m playwright install chromium

# 4) 工作台前端（可选：仓库已提交构建产物 kbserver/static；改了 webui/ 源码才需重建）
cd webui; npm install; npm run build; cd ..

# 5) 测试基线（预期：86 passed）
python -m pytest -q
```

## 1. 启动与停止服务

```powershell
.\start_kb_service.bat           # 推荐：自动读配置端口、清理同端口旧实例
.\start_kb_service.bat buildweb  # 先重建工作台前端（webui/ → kbserver/static，需 Node）再启动
python -m kbserver               # 等效手动方式
```

- 控制台出现 `Uvicorn running on http://127.0.0.1:8765` 即启动成功。
- 健康检查（浏览器或另开终端）：`Invoke-RestMethod http://127.0.0.1:8765/` → 返回 `{"service":"kbserver","version":...}`。
- **工作台 Web UI**：浏览器打开 `http://127.0.0.1:8765/app/`（六页：总览 / 检索 / 时间流 / 文档树 / 审核台 / 参数设置）。
- 停止：在服务窗口按 `Ctrl+C`。
- 首次启动会自动创建 `kb/` 五区目录（inbox / sources / collections / wiki / index.db 位置占位）。

> 以下所有命令均在**另一个终端**、仓库根目录下执行；服务窗口保持运行。

## 1b. 服务配置指南

配置有三个等价入口（单一配置入口纪律，方案文档 §11.5）：**工作台参数设置页**（推荐，掩码显示/危险项二次确认/热生效标注）、**配置文件**（启动时加载）、**API**（运行中修改）。

### 两种方式

```powershell
# 方式一：配置文件 kbserver.config.json（仓库根，手工创建/编辑）——改后需重启服务
# 方式二：API 热生效——服务运行中修改，token 等热生效项立即生效
Invoke-RestMethod -Method Put -Uri http://127.0.0.1:8765/api/config `
  -ContentType "application/json" -Body '{"config":{"token":"lan-token"}}'

# 查看当前配置（敏感项掩码显示）
Invoke-RestMethod http://127.0.0.1:8765/api/config
```

### token 专项

1. **文件方式**（需重启）：

   ```json
   { "host": "0.0.0.0", "port": 8765, "token": "lan-token" }
   ```
2. **API 方式**（立即生效，无需重启）：见上；设置后连本机 CLI/扩展也需带 token。
3. **验证**：无 token 请求 `GET /api/status` → 401；带上 `X-KB-Token: lan-token` → 200。
4. **掩码纪律**：GET 配置中 token 只显示 `******`；回传 `******` = 保持原值；日志不打印明文。
5. **各端姿势**：CLI `--token`；扩展选项页 token 栏；手机/HTTP 工具请求头 `X-KB-Token`。
6. **红线联动**：host 非环回（如 `0.0.0.0`）且 token 为空 → 服务**拒绝启动**（详见用例 10）。
7. token 泄露处置：换新值（文件或 API）即作废旧值；配置文件已入 `.gitignore`，勿提交。

> "热生效"指经 API 修改后立即起作用（管道每处理一个条目都实时读取）；经**配置文件**修改任何项都需重启。配置文件可以只写差异项，未写的用内置默认值。

### 危险项与敏感项纪律（方案文档 §11.5）

1. **库目录 `kb_root` 变更**：属危险项——需二次确认 + 自行迁移旧 `kb/` 内容（服务不会自动搬运），确认后再改并重启；不静默切换。
2. **敏感项**：`token`/`api_key` 一律掩码显示、不回显明文、不进日志、不进 git；泄露后轮换即可，影响面为外部凭据（§8 风险清单）。
3. **单一事实源**：API 修改最终也落在 `kbserver.config.json`，两种方式不产生第二事实源；直接编辑文件是允许的系统外例外。

## 2. 验收用例

### 用例 1：命令行投递 URL 并正确落盘（P0 主判据）

```powershell
python -m kbserver.cli submit "https://www.example.com" --title "验收-正文抓取"
```

预期：

1. 立即返回（受理即结束）：`{"accepted": true, "entry_id": "<12位hex>", "duplicate": false}`
2. 等待 5~15 秒（管道每 2 秒轮询 + 网络抓取），查询状态：

   ```powershell
   python -m kbserver.cli status
   ```

   预期：`sources_entries: 1`，`inbox` 全为 0，`errors` 为空。
3. 检查落盘（路径中的 id 换成上一步返回的 `entry_id`）：

   ```
   kb/sources/web/2026/<entry_id>/
   ├── note.md          # frontmatter + 正文 Markdown
   ├── raw/page.html    # 原始网页（永不覆盖）
   └── meta.json        # content_hash / original_url / raw 清单
   ```
4. `note.md` frontmatter 检查点（对照方案文档 §4.2）：

   | 字段                           | 预期                                         |
   | ------------------------------ | -------------------------------------------- |
   | `id`                         | 与`entry_id` 一致                          |
   | `platform` / `source_type` | `web` / `social`（example.com 命中兜底） |
   | `status`                     | `normalized`                               |
   | `tags`                       | `[]`（AI 未接入前恒为空）                  |
   | `url`                        | 规范化后的 URL（无追踪参数）                 |
   | `captured_at` / `title`    | 投递时间 / 投递标题                          |
5. 正文为 Markdown 提取结果（example.com 是一段英文说明文字）。

### 用例 2：HTTP API 投递（浏览器扩展 / 手机同协议）

任选一个你常读的网页 URL：

```powershell
Invoke-RestMethod -Method Post -Uri http://127.0.0.1:8765/api/capture `
  -ContentType "application/json" `
  -Body '{"url":"https://www.python.org/","title":"验收-HTTP投递","entry":"browser_ext"}'
```

预期：返回 `accepted: true`；等待管道处理后 `status` 中 `sources_entries` +1，落盘到 `sources/web/2026/<id>/`。

### 用例 3：幂等受理与去重归档

```powershell
# 再次投递与用例 1 完全相同的 URL
python -m kbserver.cli submit "https://www.example.com" --title "验收-重复投递"
```

预期：

1. 受理幂等：`entry_id` 与用例 1 相同，`duplicate: true`（不覆盖已有受理记录）。
2. 等待管道处理一轮后查 `status`：`archived: 1`；`kb/inbox/_archived/` 下出现归档目录。
3. `sources/` 下该 URL 仍只有一份 `note.md`（判重以规范化 URL 幂等）。

### 用例 4：error 态与重跑（P0 判据：失败可观测、可复活）

```powershell
# 投递一个不可达 URL（本机保留端口，必然连接失败）
python -m kbserver.cli submit "http://127.0.0.1:9/" --title "验收-error态"
```

预期：

1. 约 8 秒内三次尝试失败后转 error：`python -m kbserver.cli status` 显示 `inbox.error: 1`，`errors[]` 中含 `error_stage: "fetch"` 与 `error_message`。
2. error 详情落在 `kb/inbox/<id>/capture.json`（normalize 前无 meta.json，状态载体为 sidecar，见方案文档 §4.2）。
3. 重跑指令复活：

   ```powershell
   # <id> 换成 status 中 errors[0].id
   Invoke-RestMethod -Method Post -Uri http://127.0.0.1:8765/api/entries/<id>/rerun
   ```

   预期：返回 `{"rerun": true}`；`capture.json` 中 `status` 回到 `inbox`、`attempts` 归 0、error 字段清除。
4. 该 URL 本身不可达，重跑后仍会失败——属预期；"重跑成功复活"的完整链路由测试用例 `test_error_state_and_rerun` 覆盖。
5. 巡检完可删掉该条目：删除 `kb/inbox/<id>/` 目录。

### 用例 5：文本条目（无 URL 随手记）

```powershell
python -m kbserver.cli submit --text "验收：随手记一条想法" --title "验收-文本条目"
```

预期：落盘 `kb/sources/web/2026/t.../note.md`；`entry_id` 以 `t` 开头（时间戳+随机）；frontmatter **无** `url` 字段。

### 用例 6：token 鉴权与配置掩码

```powershell
# 设置 token（热生效）
Invoke-RestMethod -Method Put -Uri http://127.0.0.1:8765/api/config `
  -ContentType "application/json" -Body '{"config":{"token":"test-token"}}'

# 无 token 请求 → 401
Invoke-RestMethod http://127.0.0.1:8765/api/status        # 预期报 401

# 带 token → 200，且 token 掩码显示
Invoke-RestMethod http://127.0.0.1:8765/api/config -Headers @{ "X-KB-Token" = "test-token" }
# 预期 "token": "******"

# 回传掩码值 = 保持原值；清理：恢复为无鉴权
Invoke-RestMethod -Method Put -Uri http://127.0.0.1:8765/api/config `
  -Headers @{ "X-KB-Token" = "test-token" } `
  -ContentType "application/json" -Body '{"config":{"token":""}}'
```

预期：掩码不回显明文；回传 `******` 后原 token 不变（日志中同样无明文）。

### 用例 7：条目查询 API（Query API 骨架）

```powershell
Invoke-RestMethod "http://127.0.0.1:8765/api/entries"                      # 列表（含过滤参数 platform/source_type/status）
Invoke-RestMethod "http://127.0.0.1:8765/api/entries/<entry_id>"          # 详情：frontmatter + body + meta + raw_files
```

预期：列表字段与 frontmatter 一致；详情能取到正文与 meta。

### 用例 8：全文检索与索引重建（P4）

```powershell
# 检索（首次调用自动建库并懒同步；空库返回 total=0 正常）
Invoke-RestMethod "http://127.0.0.1:8765/api/search?q=%E5%88%86%E8%AF%8D" | ConvertTo-Json -Depth 5
# 预期：库中含该关键词的条目/卡片命中，返回 rel/kind/title/url/tags/snippet

# 手动全量重建（可选；index.db 可随时删除，下次检索自动重建）
Invoke-RestMethod -Method Post -Uri http://127.0.0.1:8765/api/index/rebuild
# 预期：{"rebuilt":true,"reason":"manual","docs":<库内文档数>}
```

### 用例 9：重启恢复（运维者姿态 · 方案文档 §10.5）

1. 保持 `kb/inbox/` 中存在 `status: inbox`（刚投递未处理）与 `status: error` 条目各一条。
2. 重启服务（`Ctrl+C` 后重新 `python -m kbserver`）。
3. 预期：inbox 条目被自动继续处理（断点续跑）；error 条目保持 error 等待重跑，不丢失、不静默跳过。

## 2b. P1 验收用例（投递闭环）

### 用例 10：局域网监听与安全红线（手机投递前提）

```powershell
# 1) 红线校验：非环回监听 + 无 token → 拒绝启动
#    临时把 kbserver.config.json 的 host 改为 "0.0.0.0"（token 留空）后执行：
python -m kbserver
#    预期：立即退出并提示需配置 token（安全红线：局域网监听必须带 token）

# 2) 正确姿势：host 改为 "0.0.0.0" 且配置 token（如 "lan-token"），重启服务
# 3) 手机（同一局域网）投递：浏览器访问 http://<电脑IP>:8765/ 验证可达后，
#    在快捷指令/HTTP 工具中 POST：
Invoke-RestMethod -Method Post -Uri http://<电脑IP>:8765/api/capture `
  -Headers @{ "X-KB-Token" = "lan-token" } `
  -ContentType "application/json; charset=utf-8" `
  -Body '{"url":"https://www.example.com/","entry":"mobile_share"}'
```

预期：① 无 token 拒绝启动；② 配置后服务可被手机访问；③ 带 token 投递返回 `accepted: true`，`entry` 为 `mobile_share`；④ 不带 token 的请求返回 401。桌面 CLI/扩展仍走 `127.0.0.1`，无需 token（若服务端配置了 token 则同样要带）。

### 用例 11：浏览器扩展安装与剪藏

1. 打开 `chrome://extensions`（Edge 为 `edge://extensions`）→ 开启「开发者模式」→「加载已解压的扩展程序」→ 选择仓库下 `extension/` 目录。
2. 打开扩展「选项」页（两个入口任选）：

   - **工具栏图标**：浏览器右上角拼图图标（管理扩展）→ 找到「kb buddy clipper」→ 点图钉固定 → **右键工具栏上的扩展图标 →「选项」**
   - **扩展管理页**：`chrome://extensions`（Edge 为 `edge://extensions`）→ 「kb buddy clipper」卡片 →「详情」→ 页面底部「**扩展程序选项**」
     在选项页填写：服务地址 `http://127.0.0.1:8765`，token 与服务端一致（服务端未配置 token 则留空）；建议点「**开启完成通知**」授权系统通知（可选权限，默认不申请）。
3. 在任意网页上：选中一段文字 → 右键「存入 kb buddy」（或按 `Alt+Shift+S`）。
4. 预期反馈（三层）：

   - **即时**：工具栏角标显示绿色 `OK` 约 5 秒 = 受理成功（注意：角标显示在扩展图标上，先按第 2 步把图标固定到工具栏）；服务不可达则为红色 `!` 并离线暂存
   - **约 1 分钟内**（若开启了通知）：弹「已入库 kb」；若该页提取失败则弹「该页面提取失败」并提示选中文字再剪藏
   - **命令行**：`python -m kbserver.cli status` 中 `sources_entries` +1

   > 受理成功 ≠ 入库成功：capture 受理是异步管道的第一步，SPA 页面可能随后提取失败（见用例 4 与 FAQ），结果反馈靠通知或 status 巡检。
   >
5. 打开该条目 `note.md`：正文为选中文本或页面正文，`raw/screenshot.png` 存在（受限页面如 chrome:// 除外），`meta.json` 的 `captured_from` 为 `browser_ext`。

### 用例 18：注册 collection 与全量首抓（P2c 主判据）

**推荐入口（页面操作，v0.18）**：工作台「文档树」页 → 「注册 collection」表单——解析器下拉来自注册表（`GET /api/parsers`），该解析器的必填参数（如 volcengine 的 `library_code`）自动显示；表单内含首抓耗时与 AI 整理费用提示。

| 字段            | 预期                                                     |
| --------------- | -------------------------------------------------------- |
| `id`          | `sha1(collection-id + 站内路径)` 前 12 位，跨同步稳定不变 |

### 用例 19：增量同步（幂等 + diff 三分类语义）


预期：各组文件均可打开且树序与源站侧边栏一致；`/api/collections/<id>/export` 未注册 → 404、首抓中 → 409、未知 format/images → 422。

### 用例 24：审核台看清「AI 生成了什么」+ 人工修订草稿（v0.35）

前置：已完成至少一次 AI 整理（`ai.enabled=true`，产出 draft 卡）；需**重启服务**后进入本用例（后端新增 `PUT /api/wiki/{id}`）。

1. **看 AI 产出了什么**：审核台点卡片标题展开，详情区自上而下依次给出——① AI 元信息（生成模型 / 生成时间 / 置信度 / 是否人工修订过）；② **AI 摘要**（源条目 `ai.summary`，即模型写的一句话摘要）；③ **AI 标签**（源条目 `tags`，模型打的标签）；④ 原文链接（点开原站核对）；⑤ **渲染后的卡正文**（Markdown 正常显示标题/列表/引用，不再是源码）；末尾来源行是可点链接（形如 `来源：[条目id](原站URL)`）。
2. **人工修订草稿**：draft 卡详情内点「编辑草稿」→ 修改正文 → 「保存修订」。保存后卡片出现第二枚徽标「已人工修订」，生成信息列显示「修订于 <时间>」，`status` 仍为 `draft`。
3. **修订后晋升**：点「晋升」→ 卡片转 `promoted`，成为索引与消费者的引用源。
4. **反向校验（只读核对，不改库）**：
   ```powershell
   # 修订留痕字段：edited_at 存在即"人工修订过"，ai_generated 仍为 true
   Get-Content kb\wiki\w-*.md -Encoding UTF8 | Select-String -Pattern 'edited_at|ai_generated|status:'
   ```
5. **边界预期**：promoted 卡不显示「编辑草稿」（改它须先打回重走审核）；正文清空点保存 → 提示正文不能为空（400）；不存在的卡 → 404。

预期：`ai.summary`/标签为「（无）」时说明该条目还没跑过 enrich 或模型未产出，先在文档树页对该条「整理这一条」；`status` 枚举恒为 `draft/promoted`；无任何自动晋升通道。

## 4. 常见问题

| 现象                                                 | 处理                                                                                                                                                                                                                                                                                                             |
| ---------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `connection failed`                                | 服务未启动或端口不符：核对`python -m kbserver` 是否在跑；CLI 用 `--base http://127.0.0.1:8765` 指定地址                                                                                                                                                                                                      |
| 装完依赖仍`ModuleNotFoundError`                    | venv 没装 pip，裸`pip` 沿 PATH 落到了全局 Python（看 pip 输出末尾 notice 指向的路径即可证实）。处理：`python -m ensurepip --upgrade` 先在 venv 内引导 pip，再统一用 `python -m pip install ...` 装包；重新激活 venv 后用 `pip --version` 确认指向 venv 的 Scripts 目录                                   |
| 端口被占用                                           | 编辑`kbserver.config.json`（仓库根）改 `port`，重启服务；CLI 同步换 `--base`                                                                                                                                                                                                                               |
| 控制台中文乱码                                       | PowerShell 执行`chcp 65001`，或用 `python -X utf8 -m kbserver.cli ...`                                                                                                                                                                                                                                       |
| 抓取一直 error_stage=fetch                           | 目标站点不可达或反爬；若剪藏时带了选中文本，会自动降级以选中文本落盘（`meta.json` 中 `extraction: selection_fallback`）；否则保留待重试（正文提取质量分层见方案文档 §5.3 第 2 条）                                                                                                                          |
| SPA 页面剪藏报 error_stage=extract                   | 页面为前端渲染（如 docs.volcengine.com），服务端抓到的是 JS 空壳：剪藏时**选中一段文字**再右键即可自动降级落盘（更快、不触发渲染）；未选中文本则自动走 Playwright 动态页兜底渲染重试（`playwright_fallback` 默认开），渲染成功即正常落盘（`meta.fetch.via: "playwright"`），仍失败转 error，重跑可复活 |
| 用浏览器打开`raw/page.html` 显示"404 页面无法访问" | 若该条目`meta.fetch.via` 为 `"playwright"`，raw 已是渲染后页面、可直接阅读；直连抓取的旧条目是 SPA 空壳，内嵌 JS 在本地`file://` 环境跑起来后自己渲染出报错，**不代表抓取失败**，请用文本编辑器/IDE 查看，有效内容看 `note.md`                                                                     |
| Playwright 兜底报错`playwright not installed`      | `python -m pip install -r requirements.txt` 后执行 `python -m playwright install chromium`（浏览器内核单独安装，只装一次）                                                                                                                                                                                   |
| 检索页输入任意词报 HTTP 500                         | v0.35 实跑踩坑：服务运行的那个解释器环境缺`jieba`（中文分词为延迟导入，缺装不在启动时暴露）。处理：用**启动服务的同一个解释器**执行 `"<解释器完整路径>" -m pip install -r requirements.txt` 后重启服务（先确认服务实际跑在哪个解释器环境（`Get-CimInstance Win32_Process -Filter "Name='python.exe'"` 看 `ExecutablePath`，PATH 上的`python`未必是它））；v0.36 起启动会自检并直接报出缺哪个包，语义检索缺`sqlite-vec`转 409 不再是 500 |
| 检索报 503 `index unavailable`                      | 索引库（`kb/index.db`，可重建缓存）损坏或被占用：先`POST /api/index/rebuild`重建；仍失败则删掉 `kb/index.db` 重启服务（索引会按当前库文件自动重建，语料零丢失）                                                                                                              |
| 语义检索 409（`vector index is disabled`）         | 向量增强默认关闭：参数设置页开`index.vector_enabled`（重启生效）；embedding 口径（model/dimensions）变更后 409 提示 mismatch，`POST /api/index/rebuild` 人工重建（会全量重嵌，产生外部费用）                                                                                                                 |
| 工作台打不开 / 白屏                                  | 确认`kbserver/static/index.html` 存在（构建产物随仓库提交）；若改过 `webui/` 源码，`cd webui; npm run build` 重新构建；访问入口是 `/app/` 而非 `/`                                                                                                                                                     |
| 审核台三处置的区别                                   | 晋升 = draft→promoted（进索引/图谱可引用）；打回重生成 = 删卡 + 源条目回 normalized（AI 重新生成，需`ai.enabled`）；删除 = 物理删除卡。后两者需二次确认                                                                                                                                                       |
| 想调整轮询/重试次数                                  | `kbserver.config.json` → `pipeline.poll_interval` / `pipeline.max_attempts`，保存后重启服务                                                                                                                                                                                                               |
| 想关闭图片本地化                                     | `kbserver.config.json` → `normalize.image_localization: false`                                                                                                                                                                                                                                              |
| 误删`kb/`                                          | `index.db` 可重建不慌；`sources/` 是唯一事实源，靠 §6 部署形态中的文件级备份兜底（P1 起配备份脚本）                                                                                                                                                                                                         |
| 想清空知识库重新开始                                 | 一键脚本：`.\scripts\reset_kb_full.ps1`（备份 + 停服 + 全量重置含 index.db + 重启服务 + 冒烟，加 `-Yes` 跳过确认、`-SkipBackup` 不备份）。底层脚本 `.\scripts\reset_kb.ps1 -Yes`（危险操作：删整个 `kb/` 并重建五区空目录；加 `-BackupFirst` 先自动备份；服务运行中可直接执行但 index.db 删不掉）。备份用 `backup_kb.ps1`（见用例 13）                                                                                                                                        |
| enrich 一直`error_stage=enrich`                    | 先看`meta.json` 的 `error_message`。默认走 Ollama 本地：多为 Ollama 未启动（需常驻）、模型未拉取（`ollama pull qwen2.5:1.5b` 或改 provider 默认 model 为已装模型）、首次推理加载模型超时（调大 `ai.timeout`）；GLM/云端则多为 key 未在**启动服务前**设置、地址/模型名写错、余额不足；修好后 `POST /api/entries/<id>/rerun` 复活                                                                                          |
| 想换模型后端（GLM/vLLM）                             | 工作台参数设置页 → AI 模型 → 任务分级：把对应任务的 provider 切到 glm（或自定义条目，`base_url` 手填如 `http://127.0.0.1:8000/v1`），GLM 需先设置环境变量 key；每任务独立切换，无需改代码                                                                                                                                             |
| wiki 卡不见了/重复                                   | 卡 id 确定性生成（`w-` + 源条目id+类型的哈希前 12 位），同源同类型重跑幂等覆盖，不会产生重复卡；删除卡后重跑该条目会重新生成                                                                                                                                                                                   |
| 开了`ai.enabled`但库没被整理（v0.29 起的正常行为）  | 总闸与触发已解耦：`ai.trigger_mode` 默认 `manual`——只响应页面上的「试跑（不落盘）」「整理这一条」与总览页「跑一批」；要全量自动整理需在参数设置页 → AI 模型 → 把 trigger_mode 切成 `auto`（此后按 `poll_interval` × `batch_size` 周期跑）                                                                                                                                 |
| 提示"熔断已触发"/自动整理停了                | auto 模式连续若干轮整库无成功（模型名写错、Ollama 没起、key 失效等）触发熔断，避免把全库刷成 error。修正后到参数设置页 → AI 模型 →「恢复自动整理」；手动试跑/跑一批不受熔断影响                                                                                                                                        |
| 试跑报`502`                                      | 上游模型失败（不可达/超时/返回非 JSON）：核对 Ollama 是否运行、模型是否已 `pull`；超时调大 `ai.timeout`。试跑零落盘，失败不会在库里留下任何产物                                                                                                                                                       |
